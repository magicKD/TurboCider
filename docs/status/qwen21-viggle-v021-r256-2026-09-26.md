  `Qwen-Image-2.1-viggle-turbo-v0.2.1-6step-lora-r256.safetensors` under the

  The pinned asset is about 1.3 GB. `LICENSE` and `NOTICE` were saved locally;

- No BF16 weight fusion: the separate adapter is attached at inference time,
  including separate gate and up low-rank branches of the Comfy checkpoint's
  fused `img_mlp.gate_up`. Each tested request reports 227/227 applied
  transformer projections; resident LoRA → base → LoRA preparation rebinds
  them rather than retaining stale state. Other adapters and model variants
  remain unchanged.
- Exact adapter-specific six raw sigma nodes plus Qwen resolution shift and
  zero endpoint, with no base-model terminal stretch. The 512²/six-step/scale-1
  GPU route supports text-to-image and 1–3 ordered full-size (1024px encoding)
  editing references. Requires explicit approximation opt-in; W8A8 GPU/ANE
  and final-step FFN reuse are not validated with this student.

## Timings and comparisons

All timings below are seconds for prepared **resident** Session requests after
warmup and with `prompt_cache_hit=true`, on the local M4 Max at 512×512.
They include denoising, VAE decode, and PNG export; they are *not* one-shot CLI
or first-request times. The six-step diagnostic requests also wrote tensors,
whereas the 40-step control did not; this small I/O mismatch makes the
cross-step speed ratios indicative, not a controlled isolated kernel ratio.

| Same prompt, references and seed | GPU request wall | Denoising | Observed relation |
|---|---:|---:|---:|
| Fox, ordinary BF16, 40 steps | 43.180 / 43.157 | 42.567 / 42.556 | control |
| Fox, ordinary BF16, 6 steps | 7.073 / 7.049 | 6.466 / 6.463 | **not** the trained six-step student |
| Fox, Viggle r256, 6 steps | 8.187 / 8.229 | 7.604 / 7.633 | about **5.26×** versus 40-step control, but **0.860×** versus naive 6-step GPU |
| One full-size reference, Viggle r256, 6 steps | 14.705 / 14.719 | 14.102 / 14.132 | only student run; no matched 40-step control |
| Two full-size references, ordinary BF16, 40 steps | 68.480 (one run) | 67.868 | control |
| Two full-size references, Viggle r256, 6 steps | 21.926 / 21.948 | 21.334 / 21.356 | about **3.12×** versus 40-step control (one control run) |
| Three full-size references, Viggle r256, 6 steps | 30.110 / 29.974 | 29.522 / 29.385 | only student runs; no matched 40-step control |

For the same six-step fox input, both compared runs have byte-identical
dumped text and initial noise tensors, 227 applied Viggle projections, and
zero reference tensors. The ordinary and Viggle **six-step** final RGB images
have correlation 0.824/RMSE 0.192; that is a large *different-model/schedule*
comparison, not an error metric against ground truth. The two-reference
Viggle-versus-40-step-base RGB correlation is 0.921/RMSE 0.115; pixel errors
also include composition and viewpoint changes and cannot alone determine
whether an edit is acceptable.

The separate BF16+W8A8 6144-channel mixed-route 40-step fox benchmark in
`docs/status/qwen21-w8a8-6144-t2i.md` measured around 30.48 s, versus
8.21 s for this six-step GPU student. **Do not call this a strict 3.7× ANE
kernel acceleration**: different student, schedule, steps, precision and
image result. The 40-step W8A8 edit benchmark resizes references to 256px,
so it is *not* comparable to this student's 1024px-reference editing input.
The separate W8A8 W8A16-vs-BF16 GPU suffix test at 512²/two-reference/5-step
favored the BF16 suffix (5.420/5.437 versus 5.768/6.022 seconds, ratio
0.921×). Thus int8 hardware arithmetic alone does not establish a faster
end-to-end route for the runtime adapter; an adapter-aware Core ML export and
same-input quality/placement validation would be required.

## GPU kernel follow-up

The existing opt-in fused Q/K RMSNorm+RoPE Metal kernel, set through
`TURBOCIDER_QWEN21_METAL_QK_NORM_ROPE=1`, gave 8.033 / 7.996 seconds on the
same Viggle fox prompt, a **1.024×** median request-wall speedup over the
8.187 / 8.229-second unfused adapter run. Dumped text and initial noise
tensors matched; output RGB correlation was 0.99908/RMSE 0.01122, not bit
identical. On the full-size **two-reference** edit, fused Q/K measured
21.471 / 21.385 seconds versus 21.926 / 21.948 (about **1.024×**), with
identical dumped text/noise/both reference tensors and output RGB correlation
0.99643/RMSE 0.02412. The two teapot subjects and composition are preserved
on visual inspection; finer glaze/spout pixels change. This remains an
explicit approximation rather than the default.

An additional `TURBOCIDER_QWEN21_VIGGLE_LORA_FP16=1` experiment narrows only
the low-rank LoRA matmuls to FP16, then widens their output before accumulation
against the BF16 base path. Alone on the fox it measured 7.960/8.100 seconds,
about **1.022×** versus plain Viggle, with RGB correlation 0.99918/RMSE
0.01068. With *both* FP16 LoRA and fused Q/K set, matched fox requests took
7.882/7.858 seconds, **1.043×** versus plain Viggle; RGB correlation
0.99965/RMSE 0.00695. The combined two-reference edit took 20.988/21.044
seconds, **1.044×** versus plain Viggle; RGB correlation 0.99885/RMSE
0.01365. For both combined comparisons the dumped text/noise/reference
tensors matched exactly and the output subjects remained visually similar.
Even this combination is still a small speed-first diagnostic: it has not
passed quality assessment on diverse prompts or seeds. Keep both switches
default-off and the normal FP32 LoRA branch intact.
One additional prepared, cached run each of **one** and **three** full-size
references measured **14.147 s** versus plain 14.705 s (**1.039×**) and
**28.695 s** versus plain 30.110 s (**1.049×**), respectively; metadata and
227 LoRA projections matched, but these two cases did **not** dump input
tensors. Output RGB correlations were 0.99985/0.99888. The one-reference
teapot still misses the matte material request and the three-reference
sticker is still a face close-up; the extra kernel/precision settings do not
solve those edit-fidelity limitations.

## Visual check / artifacts

- Text-to-image: `results/qwen21/viggle-v021-r256-t2i-512-6.png` and
  `results/qwen21/session-viggle-v021-r256-control-512-40/run-0.png` both
  clearly show a fox in snow, with different expression, orientation and
  snow/foliage details. One prompt is not broad fidelity validation.
- Single reference: `results/qwen21/viggle-v021-r256-edit1-512-6.png` retains
  the teapot shape, handle and lid, but **does not obey the requested matte
  finish** (strong glaze highlights). Do not mark this edit as a pass.
- Two references: `results/qwen21/viggle-v021-r256-edit2-512-6.png` versus
  `results/qwen21/session-viggle-v021-r256-edit2-control-512-40/run-0.png`:
  beige left and blue right teapots recognizable with warm wood table, but
  spout/handle angles and glazes differ. The object-level composition may be
  acceptable if exact material/shape matching is not required.
- Three references: `results/qwen21/viggle-v021-r256-edit3-512-6.png`
  preserves two teapots and an illustrated orange sticker in the center, but
  redraws the third reference as a dragon *head* rather than preserving its
  full sticker appearance. Not a strict reference-fidelity pass.

Source requests are `results/qwen21/viggle-v021-r256-*-request.json`; six-step
timing reports and dumped tensors reside under
`results/qwen21/session-viggle-v021-r256-*/`. These paths are generated and
Git-ignored. Overall the six-step student is useful for speed-first creation
and looser composition, not yet for detail-critical or identity-preserving
editing. Retain the standard BF16 GPU path and the independently tested
W8A8 experiments; do not replace their default selection based on one seed.
