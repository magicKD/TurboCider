# Qwen-Image-2.1 base：矩形画布复用 512² W8A8 图（2026-09-27）

## 路由与边界

显式 `TURBOCIDER_QWEN21_RECT_W8A8_DIAGNOSTIC=1` 才允许
`768×512`／`512×768` 输出、20–40 步、base checkpoint、BF16 GPU
后缀 + W8A8 Core ML 前 6144 通道，文生图或 1–3 张原尺寸参考图编辑。
不允许 Viggle LoRA、W8A16 GPU 后缀、GPU-only 层 fallback、跨请求
prefix KV 或末步 FFN 复用；标记为诊断路线而非公开默认推荐。输入
manifest 必须与 base checkpoint SHA 匹配、32 层、1024 行、6144 通道。

初始 prefill 继续完整 BF16 GPU，保持 text/reference prefix-KV 不变；
后续每个 decode 步的 1536 个目标 token 对每层 FFN 拆为 1024+512 行。
第二块在行尾补零，调用同一个固定 1024-row Core ML 图，随后裁回
512 行；GPU 后缀也沿用相同分块。每请求预期 `19 × 32 × 2 = 1216`
次 Core ML 推理（20 步；40 步为 2496 次），`HybridSession` 仍报告
graph bucket=1024，
不是动态重编译 1536-row ANE 图。分块量化与完整 BF16 GPU 不等价，
因此必须比较 PNG 并记录有损近似。`cpuAndNeuralEngine` 计算单元策略
不能证明推理实际全部驻留 ANE。

## 初步 20 步同输入比较

M4 Max；同 checkpoint、prompt「木桌上的陶瓷茶壶」、seed 42，
各自 resident Session 已独立完成**同为 20 步**的完整预热，
下表均为此后**仅一次**包含 VAE/PNG 的 warm 请求。比较器校验了
text/noise safetensors 张量相同、输出尺寸相同、manifest provenance、
hybrid 每请求 1216 次预测且零运行失败。

| 输出画布 | BF16 GPU 墙钟 | W8A8 hybrid 墙钟 | 相对同形状 GPU | RGB RMSE／相关系数 |
| --- | ---: | ---: | ---: | ---: |
| 768×512 | 33.256 s | 28.907 s | 1.150× | 6.02/255／0.99339 |
| 512×768 | 33.343 s | 29.094 s | 1.146× | 6.57/255／0.99226 |
| 768×512，一图编辑（原尺寸 1024px 蓝色茶壶） | 43.376 s | 39.076 s | 1.110× | 13.87/255／0.97937 |

两组输出人工并排查看，茶壶主体、壶嘴／把手、木桌构图保持；釉面
颗粒、壶盖边缘及阴影有局部变化。横向基线自己生成了非典型的
双壶嘴茶壶，候选没有额外改变这一布局，不应误称语义质量合格。
一图编辑中两侧釉面的涂抹/纹理差异比文生图明显，但蓝壶主体、
壶嘴、把手和木桌仍可辨；基线自己也将透明材质画成偏厚的蓝釉，
不能把它解释成编辑材质保真已经合格。该配对使用原尺寸参考图，
两边输入张量一致，hybrid 仍为请求内 1216 次 Core ML 推理、零错误。
实验 JSON/PNG 与比对报告保存在忽略的临时目录，不进入 Git。

## 40 步文生图及 DBCache 叠加（两个矩形方向）

扩展 DBCache 的显式门禁到矩形 base GPU，以及已开启矩形 W8A8
诊断的 hybrid；沿用阈值 `0.25`、最多连续跳过 `8` 步，默认仍未开启。
不重新编译 Core ML 图。各 Session 独立完整 40 步预热后，仅一次
warm 请求；每个方向的四路 prompt、seed 42、text/noise 张量逐字节相同，
墙钟包含 VAE/PNG，不包含模型首次加载。

| 画布和路线 | warm 墙钟 | 相对同路线无缓存 | DBCache 跳步／Core ML 请求调用 |
| --- | ---: | ---: | ---: |
| 768×512 BF16 GPU | 65.763 s | 基线 | 0／0 |
| 768×512 GPU + DBCache | 31.902 s | 2.061× | 28／0 |
| 768×512 W8A8 hybrid | 56.164 s | 基线 | 0／2496 |
| 768×512 hybrid + DBCache | 26.972 s | 2.082× | 28／1152 |
| 512×768 BF16 GPU | 65.680 s | 基线 | 0／0 |
| 512×768 GPU + DBCache | 31.951 s | 2.056× | 28／0 |
| 512×768 W8A8 hybrid | 56.768 s | 基线 | 0／2496 |
| 512×768 hybrid + DBCache | 27.500 s | 2.064× | 28／1152 |

缓存 hybrid 对缓存 GPU 横向约 `1.183×`、纵向约 `1.162×`，
但每个方向仍是单 prompt/seed/测量。
28 步 × 24 中间层 × 每层两次 Core ML 调用，恰好解释
`2496 → 1152`；两路 hybrid 均零运行失败。各自缓存前后肉眼仍是
完整陶瓷茶壶、壶嘴、把手与桌面，表面颗粒和盘子边缘变化；
跨 GPU/hybrid 路由的壶嘴／盘子形状变化更明显，但此文生图样本的
主体和构图仍接近。纵向样本的茶壶、壶嘴、把手、盖沿与木桌也
保留，釉面与盖沿纹理有变化。不能用像素相关性替代手工检查，
也不能把这组文生图质量结论外推到参考图编辑。

## 20 步原尺寸两图编辑（768×512）

米色茶壶和蓝色茶壶为有序原尺寸 1024px 参考图，同 prompt、seed 17。
四个独立 Session 都完成完整 20 步预热后，仅一次 warm 请求；
比较器核对 text/noise/两张 reference tensors 逐字节相同。

| 路线 | 请求墙钟 | 对本路线无缓存 | 本请求 Core ML 调用 |
| --- | ---: | ---: | ---: |
| BF16 GPU | 54.259 s | 基线 | 0 |
| GPU + DBCache 0.25/max=8 | 38.191 s | 1.421× | 0 |
| W8A8 hybrid | 50.627 s | 基线 | 1216 |
| hybrid + DBCache 0.25/max=8 | 35.621 s | 1.421× | 736 |

两路缓存各跳过 10 个 decode 步、节省 240 个中间层；hybrid
每层目标行分两次预测，因此调用数下降 480，两路 hybrid 均零
运行失败。缓存 hybrid 相对缓存 GPU 仅 `1.072×`，不能由单次
实验称作稳定的编辑加速优势。人工并排看米壶左、蓝壶右、
壶盖、壶嘴和把手都保持；两路的蓝壶质地／阴影和壶身亮度
略不同，按主体与布局的肉眼标准仍可接受。不代表对小文字、
特定材质或其它编辑指令的忠实程度。

三张原尺寸参考图的同画布纯 GPU 20 步可运行：本次另一提示
下无缓存 `65.934 s`、DBCache `47.808 s`（`1.379×`），
三主体与贴纸眼睛／白边肉眼保留，输入张量相同。但 resident
hybrid 被保守的物理内存估算在推理前拒绝：64 GiB 机器上，
计划估算约 61.25 GiB，再加 4 GiB 的系统余量超过物理内存；
不能绕过此门禁后声称三图 resident hybrid 成功或提供其 warm 倍速。

同一三图请求在生产 CLI 的 `component_staged` 模式确实可运行。
同样开启 DBCache、阈值 `0.25`／连续上限 `8`，独立冷请求
GPU `58.403 s`、hybrid `63.935 s`（GPU/hybrid `0.913×`）；
后者仅 Core ML 加载／路由准备就报告约 `8.594 s`，抵消了
decode 收益，**不能**与前面的 resident warm 时间相除。
两次请求 prompt、seed 和有序参考文件相同，但此次没有两边
逐字节输入 tensor dump，故不宣称严格相同的内部条件；
GPU staged PNG 与上述同设置 resident GPU 缓存 PNG 的 SHA-256
相同。两张 staged 图人工查看米壶、蓝壶和橙龙贴纸的眼睛／白边
均保留，局部壶面及阴影变化。三图 staged hybrid 的完整功能
已验证，但在此机器／请求上不是最快路线；需要完整输入验证和
交错冷请求重复，不能将它设为默认推荐。

## 后续门禁

尚缺不同提示词／种子、重复 ABBA／中位数、40 步参考图编辑、
纵向 2–3 图编辑与横向三图 resident hybrid 的
质量与速度配对，尤其检查参考物体是否丢失。预热/manifest 加载不计
入上表，不适用于冷启动比较。LoRA + base ANE 仍未接入本路线，
DBCache 已支持两个矩形方向的显式叠加，但尚缺纵向编辑门禁。
因此当前证明两种方向在 20 步单样本文生图可复用同一个 Core ML
图，横向 40 步缓存文生图及 20 步两图编辑有进一步收益；
不能推广为默认质量／速度保证。
